The NaviGator platform deploys in two parts: the React PWA (`itinerary-builder`) and the backend services (`navigator_services`). Both use GitHub Actions workflows that trigger on merged pull requests, but they use different deployment strategies. The frontend uses a blue-green Docker setup with zero-downtime switching, while the services layer deploys with PM2 on the same host.

## Deployment Overview

| Component | Repo | Trigger | Strategy | Host Path |
| --- | --- | --- | --- | --- |
| PWA (frontend) | `itinerary-builder` | PR merged to `development` | Blue-green Docker containers | `/opt/navigator` |
| Services (backend) | `navigator_services` | PR merged to `main` | PM2 reload | `/opt/navigator_tapis` |

Both workflows run on a self-hosted GitHub Actions runner and connect to the production server over SSH.

## Frontend Blue-Green Deployment

The PWA deploys from the `itinerary-builder` repository using a blue-green pattern. Two identical frontend containers (`frontend-blue` and `frontend-green`) exist at all times, but only one serves traffic at a time through an nginx proxy.

### How the Switch Works

The proxy container reads an `ACTIVE_HOST` environment variable to decide which upstream container receives traffic. The deploy workflow (`deploy.yaml`) inspects the currently active slot, builds and starts the inactive one, verifies it is healthy, then reconfigures the proxy and tears down the old slot.

The switching logic from `.github/workflows/deploy.yaml`:

1. Read `ACTIVE_HOST` from the running proxy container's environment.
2. If `ACTIVE_HOST` is `frontend-blue:80`, target `frontend-green`; otherwise target `frontend-blue`.
3. Build the inactive slot with the new commit's version and SHA.
4. Start the inactive slot and confirm its container status is `running`.
5. Restart the proxy with `ACTIVE_HOST` pointing at the new slot.
6. Stop and remove the old slot.

If the new container fails to reach `running` status, the workflow exits before switching the proxy, leaving the current slot active.

### Docker Compose Services

The `docker-compose.yaml` defines three services:

- `proxy`: An nginx:alpine container that exposes port `443` and forwards traffic to the active frontend host. It mounts the proxy nginx config, a TLS certificate, and a private key.
- `frontend-blue` and `frontend-green`: Two identical build targets that compile the Vite React app and serve it with nginx on port `80`.

Both frontend services accept `VITE_APP_VERSION` and `VITE_GIT_SHA` as build args. The deploy script sets these from `package.json` version plus the short git SHA so every build is traceable.

### Proxy Configuration

The proxy nginx config (`proxy-nginx.conf`) defines a single upstream named `frontend` that resolves to `${ACTIVE_HOST}` at runtime. It listens on `443` with SSL for `pathfinder.isco-pipe.com` and proxies requests to the active container.

The frontend container config (`app-nginx.conf`) is a standard static-file server on port `80` with `try_files` fallback to `index.html` for client-side routing.

### Build-Time Versioning

The `Dockerfile` is a multi-stage build:

1. **Build stage** (`node:22`): installs dependencies with `npm ci`, copies source, and runs `npm run build`.
2. **Serve stage** (`nginx:alpine`): copies the `dist` output and `app-nginx.conf` into the image.

Build args `VITE_APP_VERSION` and `VITE_GIT_SHA` are passed through both stages and stored as container labels (`org.opencontainers.image.version` and `org.opencontainers.image.revision`).

## Services Deployment

The backend services in `navigator_services` deploy with a simpler PM2-based flow defined in `.github/workflows/deploy.yml`.

### Deploy Steps

1. SSH into the server and reset the working directory (`/opt/navigator_tapis`) to the latest `main` commit.
2. Run `npm ci` to install dependencies.
3. Run `npm run build` to compile TypeScript.
4. Run `pm2 reload ecosystem.config.js` to restart the application cluster.

### PM2 Configuration

The `ecosystem.config.js` file defines a single app named `navigator_services`:

- `script`: `./dist/server.js`
- `watch`: `false` (disabled because `tsc` rebuilds `dist/` during deploy, which would otherwise trigger repeated restarts)
- `instances`: `1`
- `exec_mode`: `cluster`
- `env.NODE_ENV`: `production`

Using `pm2 reload` performs a zero-downtime restart by spawning a new process before stopping the old one.

## CI Workflows and Secrets

Both repos use GitHub Actions workflows that run on self-hosted runners. The workflows share the same SSH setup pattern but target different branches and host paths.

### Required Secrets

The workflows reference the following repository secrets by name. These must be configured in each repo's GitHub settings:

- `SSH_KEY`: Private SSH key for authenticating to the deployment server.
- `SSH_USER`: Username for the SSH connection.
- `HOST_IP`: IP address or hostname of the deployment server.
- `HOST_PORT`: SSH port on the deployment server.

### Frontend Workflow (`deploy.yaml`)

Triggered when a pull request to `development` is closed and merged. The job is named `Blue-Green Deploy`. It sets up SSH, pulls the latest code, and runs the blue-green deploy script remotely.

### Services Workflow (`deploy.yml`)

Triggered when a pull request to `main` is closed and merged. The job is named `Git pull and Run Script`. It sets up SSH, pulls the latest code, installs dependencies, builds, and reloads PM2.

### Test Workflow (`test.yaml`)

The `itinerary-builder` repo also runs unit tests on every pull request to `development` or `main` using `vitest`. The workflow installs Node 22, runs `npm ci`, and executes `npm run test:run`. Playwright end-to-end tests under `e2e/` are excluded from CI because they require a running app and an authenticated session.

## Rollback Behavior

- **Frontend**: If the new container fails to start, the proxy is never switched, so traffic continues to the previously active slot. To roll back manually, an operator can set `ACTIVE_HOST` back to the previous slot and restart the proxy container.
- **Services**: `pm2 reload` keeps the old process alive until the new one is ready. If the new build fails to start, PM2 retains the previous process. You can also run `pm2 reload ecosystem.config.js` again after fixing the code, or use `pm2 revert` to restore the last stable snapshot.
