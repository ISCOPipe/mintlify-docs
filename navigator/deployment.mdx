ISCO NaviGator has separate frontend and backend deployments. The [October 15, 2026 ADO infrastructure handoff](https://dev.azure.com/ISCO-PIPE/af08c6ac-ebae-4d0a-bf50-811762d53dd2/_wiki/wikis/3688edc8-fba5-407c-926f-78e7f119e792?pagePath=%2FIT%20Development%20Documentation%2FHandoffs%2FWilliam%20Lemay%20-%20Infra) identifies the `main` frontend as an AWS Amplify site at `https://navigator.isco-pipe.com`, the `development` frontend as a blue-green Docker deployment on Pathfinder, and `navigator_services/main` as a PM2 application. This hosting inventory is wiki guidance, not a live deployment check. The Docker workflow below does not establish the production Amplify release process.

## Deployment overview

| Component | Repo | Trigger | Strategy | Host Path |
| --- | --- | --- | --- | --- |
| Development PWA | `itinerary-builder` | PR merged to `development` | Blue-green Docker via root-owned script | `/opt/navigator` |
| Production PWA | `itinerary-builder` | Confirm in Amplify; wiki maps `main` to this site | AWS Amplify, per handoff | Not a Pathfinder docroot |
| Services (backend) | `navigator_services` | PR merged to `main` | PM2 reload | `/opt/navigator_tapis` |

The development Docker and backend PM2 workflows use a self-hosted GitHub Actions runner and SSH to Pathfinder. Do not infer Amplify's build or rollback settings from either workflow.

## Development frontend deployment

The [ADO Docker deployment handoff](https://dev.azure.com/ISCO-PIPE/af08c6ac-ebae-4d0a-bf50-811762d53dd2/_wiki/wikis/3688edc8-fba5-407c-926f-78e7f119e792?pagePath=%2FIT%20Development%20Documentation%2FHandoffs%2FWilliam%20Lemay%20-%20Docker%20deploys) documents the root-owned scripts and Compose files in [ISCOPipe/docker_scripts](https://github.com/ISCOPipe/docker_scripts). The deployment account must not receive general Docker access to fix a permission failure.

The [workflow inspected on `main` at `6ad7e82`](https://github.com/ISCOPipe/itinerary-builder/blob/6ad7e8280e564260a8f459ae2864eb1859e40ec6/.github/workflows/deploy.yaml) now matches the script-based deployment path: it updates `/opt/navigator` to `origin/development`, then invokes `sudo -n /opt/docker_scripts/deploy_navigator.sh`. Its trigger remains a merged PR to `development`; finding this workflow on `main` does not make it an Amplify production workflow.

The script alternates `frontend-blue` and `frontend-green` behind an nginx proxy. It starts the inactive slot before switching and removes the old slot afterwards; both slots do not remain running indefinitely.

### How the switch works

The proxy reads `ACTIVE_HOST` to select its upstream. The root-owned script performs the following sequence, also described in the [deployment repository's Navigator section](https://github.com/ISCOPipe/docker_scripts#navigator):

1. Read `ACTIVE_HOST` from the running proxy container's environment.
2. If `ACTIVE_HOST` is `frontend-blue:80`, target `frontend-green`; otherwise target `frontend-blue`.
3. Build the inactive slot with the new commit's version and SHA.
4. Start the inactive slot and confirm its container status is `running`.
5. Restart the proxy with `ACTIVE_HOST` pointing at the new slot.
6. Stop and remove the old slot.

If the new container fails to reach `running` status, the workflow exits before switching the proxy, leaving the current slot active.

### Docker Compose services

The deployment-owned `/opt/docker_scripts/navigator/docker-compose.yaml` defines three services. The app repository no longer contains its own Compose file, proxy config, or PM2 config.

- `proxy`: An nginx:alpine container that exposes port `443` and forwards traffic to the active frontend host. It mounts the proxy nginx config, a TLS certificate, and a private key.
- `frontend-blue` and `frontend-green`: Two identical build targets that compile the Vite React app and serve it with nginx on port `80`.

Both frontend services accept `VITE_APP_VERSION` and `VITE_GIT_SHA` as build args. The deploy script sets these from `package.json` version plus the short git SHA so every build is traceable.

### Proxy configuration

The deployment-owned proxy config is `/opt/docker_scripts/navigator/proxy-nginx.conf`. It routes Pathfinder traffic to the active frontend slot. Maintain privileged scripts, Compose files, and proxy configuration through reviewed changes in the deployment repository, not by editing the app checkout or server files.

The [October 16 Docker handoff](https://dev.azure.com/ISCO-PIPE/af08c6ac-ebae-4d0a-bf50-811762d53dd2/_wiki/wikis/3688edc8-fba5-407c-926f-78e7f119e792?pageId=693) supersedes the earlier manual-pull guidance. After changes reach `docker_scripts/main`, its sync workflow calls the root-owned, no-argument `sudo /usr/local/sbin/sync_docker_scripts.sh` to reset `/opt/docker_scripts` to `origin/main`. Check that sync separately, then run the authorized app-specific deploy script to apply the files. **Sync does not redeploy.** A new app requires an administrator to add its app-specific sudoers rule; do not grant general Docker or sudo access.

The frontend container config (`app-nginx.conf`) is a standard static-file server on port `80` with `try_files` fallback to `index.html` for client-side routing.

### Build-time versioning

The `Dockerfile` is a multi-stage build:

1. **Build stage** (`node:22`): installs dependencies with `npm ci`, copies source, and runs `npm run build`.
2. **Serve stage** (`nginx:alpine`): copies the `dist` output and `app-nginx.conf` into the image.

Build args `VITE_APP_VERSION` and `VITE_GIT_SHA` are passed through both stages and stored as container labels (`org.opencontainers.image.version` and `org.opencontainers.image.revision`).

## Services deployment

The backend services in `navigator_services` deploy with a simpler PM2-based flow defined in `.github/workflows/deploy.yml`.

### Deploy steps

1. SSH into the server and reset the working directory (`/opt/navigator_tapis`) to the latest `main` commit.
2. Run `npm ci` to install dependencies.
3. Run `npm run build` to compile TypeScript.
4. Run `pm2 reload ecosystem.config.js` to restart the application cluster.

### PM2 configuration

The `ecosystem.config.js` file defines a single app named `navigator_services`:

- `script`: `./dist/server.js`
- `watch`: `false` (disabled because `tsc` rebuilds `dist/` during deploy, which would otherwise trigger repeated restarts)
- `instances`: `1`
- `exec_mode`: `cluster`
- `env.NODE_ENV`: `production`

PM2 cluster reload starts a replacement process before stopping the old one. Verify application health after the reload; this setting alone does not prove uninterrupted service.

## CI workflows and secrets

Both repos use GitHub Actions workflows that run on self-hosted runners. The workflows share the same SSH setup pattern but target different branches and host paths.

### Required secrets

The workflows reference the following repository secrets by name. These must be configured in each repo's GitHub settings:

- `SSH_KEY`: Private SSH key for authenticating to the deployment server.
- `SSH_USER`: Username for the SSH connection.
- `HOST_IP`: IP address or hostname of the deployment server.
- `HOST_PORT`: SSH port on the deployment server.

### Development frontend workflow (`deploy.yaml`)

Triggered when a pull request to `development` is closed and merged. The job is named **Blue-Green Deploy**. It sets up SSH, updates the app checkout, and calls the root-owned deploy script remotely.

### Services workflow (`deploy.yml`)

Triggered when a pull request to `main` is closed and merged. The job is named **Git pull and Run Script**. It sets up SSH, pulls the latest code, installs dependencies, builds, and reloads PM2.

### Test workflow (`test.yaml`)

The `itinerary-builder` repo also runs unit tests on every pull request to `development` or `main` using `vitest`. The workflow installs Node 22, runs `npm ci`, and executes `npm run test:run`. Playwright end-to-end tests under `e2e/` are excluded from CI because they require a running app and an authenticated session.

## Rollback limits

- **Development frontend:** a startup failure before the switch leaves the active slot unchanged. The check is container status `running`, not an end-to-end health test. After a successful switch, the old slot is removed; changing `ACTIVE_HOST` back can target a missing container. Follow the [deployment repository's rollback procedure](https://github.com/ISCOPipe/docker_scripts#rolling-back-an-app): restore a known-good app revision and redeploy through the approved script. Do not run a bare proxy Compose command that resets the slot selection.
- **Production frontend:** the cited handoff identifies Amplify hosting but does not document a verified rollback procedure. Do not apply the Docker procedure to this site.
- **Services:** `pm2 reload` is a process reload, not a versioned application rollback. Restore a known-good source/build through the reviewed deployment process and verify health. Do not assume a reload failure restores all application files.
